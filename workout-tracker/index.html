Workout Tracker

Google Sheets Apps Script Mobile Web App

A private strength-training tracker that began as a spreadsheet and became a mobile web app after a single prompt.

Open the demo Read Personal OS

What I Was Solving

The tracker needed to support the way I actually train: planned sessions, substitutions, skipped work, previous performance, mesocycle progression, and enough structure to review patterns over time. Google Sheets was already the source of truth, but using the sheet directly on a phone was too slow and fiddly for the middle of a workout.

I also wanted to test something specific: what could Codex build from a lightweight MVP brief, my existing workout tracker files, a UI screenshot from a workout app I liked, and one prompt? I sent it off, went to sleep, and woke up to a working app.

What I Built

The production system is a private Google Sheet with Apps Script logic and a mobile-first web interface. The Sheet remains the database and review surface; the web app handles the workout flow, draft state, validation, completion, and recovery paths.

It was relatively easy to get a usable first version because the logic was not starting from zero. The spreadsheet tabs already held the important structure: programs, sessions, exercise history, volume targets, mesocycles, and logged performance. Codex mostly had to read that existing system and wrap it in a phone-friendly interface.

The first pass did not look exactly like the current version, and it did not have the anatomical training-distribution image yet. But it was close enough that I spent about 10 minutes fixing mobile bugs and used it that same morning to track my first workout through the app.

The shareable demo is generated separately as one standalone HTML file. It inlines the app shell, styles, shared workout engines and a mock backend, so people can try the interaction without touching the live Google Sheet or Apps Script deployment.

The demo intentionally includes realistic workout metrics. That makes testing more useful: the interface has to handle real session names, previous-performance values, substitutions, skipped work, and completion flows rather than toy examples.

Interactive SVG

The completed-workout screen uses an anatomical SVG rather than a static image. Each muscle region is addressable by name, so the app can highlight the muscles worked in a completed session and compare that workout with the rest of the week.

The interactive version below is not part of the app itself. I created it as a review tool to test the mapping Codex had done between the spreadsheet's muscle groups and the individual SVG paths before connecting the body map to workout data.

Key Decisions

  • Keep the spreadsheet as the source of truth. The project did not need a new database. It needed a better interface over a system that already worked, with the core workout logic already expressed in Sheet tabs and Apps Script.
  • Use the first build as a capability test. The initial app came from one prompt, preexisting tracker files, a short MVP brief, and a visual reference. That made the project a practical test of how far Codex could get without a long back-and-forth specification process.
  • Separate the private app from the public demo. The real deployment is tied to my Google account and training history. The demo uses mock data and local browser storage.
  • Reuse shared logic where possible. Validation and workout-domain helpers are pulled into the demo so the public version stays close to the real app without exposing private persistence code.
  • Add the anatomical view after the core workflow worked. The training-distribution SVG was a later refinement that turns completed sets into something easier to scan than a table. I also built a separate interactive SVG review page to check that Codex had mapped each muscle group to the right body paths before the visualization was used in the app.

Different From Personal OS

Personal OS was mostly an information architecture problem: how to make context durable enough for AI collaboration. Workout Tracker was a product and workflow problem: how to make a private, real-data system usable in the moment, on a phone, while preserving the reliability of the underlying Sheet.
